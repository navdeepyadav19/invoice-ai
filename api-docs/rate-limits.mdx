Rate limits apply **per API key**, so one integration's runaway loop can't use up another integration's budget.

## Limits

| Bucket | Applies to | Limit |
|---|---|---|
| `request` | Every authenticated endpoint except `send` | **120 requests per 60 seconds** |
| `send` | `POST /invoices/{id}/send` | **10 requests per hour** (3,600 seconds) |

Sending is limited much more tightly because each send costs money, lands in a third party's inbox, and is the first thing a stolen key would be used for. The two buckets are counted separately, so a `send` call doesn't count toward the 120-per-minute budget.

Windows are fixed. The count starts with your first request and resets when the window ends. Requests that fail authentication (`401`) are rejected before rate limiting, so they don't count. `GET /openapi.json` isn't rate limited by the API.

## Response headers

Every authenticated response, whether it succeeds or fails, includes the state of the bucket it used:

| Header | Meaning |
|---|---|
| `RateLimit-Limit` | The bucket's limit, for example `120`. |
| `RateLimit-Remaining` | Requests left in the current window. |
| `RateLimit-Reset` | When the window resets, as a **Unix timestamp in seconds**. |

```http
HTTP/1.1 200 OK
RateLimit-Limit: 120
RateLimit-Remaining: 117
RateLimit-Reset: 1789371294
X-Request-Id: req_4f0c2a9e8b7d4c1fa3e2b6d9c0e1f2a3
```

<Note>
  `RateLimit-Reset` is an absolute timestamp, not a number of seconds from now. For a relative wait, use `Retry-After` on a `429`.
</Note>

## When you go over

You get `429 Too Many Requests` with `code: "rate_limited"` and a `Retry-After` header that gives the number of seconds to wait (at least `1`):

```json
{
  "type": "https://invoice.horizonpay.co/problems/rate-limited",
  "title": "Too many requests",
  "status": 429,
  "detail": "Rate limit of 120 per 60s exceeded.",
  "instance": "req_…",
  "code": "rate_limited"
}
```

## Staying under the limit

- **Watch `RateLimit-Remaining`** and slow down before it reaches `0`, rather than waiting for a `429`.
- **On a `429`, wait `Retry-After` seconds**, then retry. When you retry a write, reuse the same `Idempotency-Key`.
- **Use `limit=100` on list endpoints** to fetch more per request.
- **Use webhooks instead of polling** to hear about views, payments and voids.

<Warning>
  Limits are currently counted per server instance. Under load, the limit you actually hit can be higher than the documented numbers. Don't rely on that: design for 120 per minute and 10 sends per hour, since the counting may tighten without notice.
</Warning>
