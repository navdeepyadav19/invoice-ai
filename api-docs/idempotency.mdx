---
title: "Idempotency"
description: "Retry writes safely with the Idempotency-Key header, so a lost response never spends a second invoice number."
icon: "arrows-rotate"
---

Networks drop responses. If you send "finalize this invoice", we assign number `INV-0042`, and the response never reaches you, a naive retry would assign `INV-0043`. That leaves a permanent gap in a series that has to stay consecutive.

An `Idempotency-Key` header prevents this. Send a unique key with a write, and if you retry with the **same key and the same body**, you get the original response back instead of the work running again.

```bash
curl -X POST https://invoice.horizonpay.co/api/v1/invoices/in_.../finalize \
  -H "Authorization: Bearer $INVOICE_AI_API_KEY" \
  -H "Idempotency-Key: 8e0f4b1c-6f55-4c37-9d0b-2a7f5f0c9e21"
```

## Which endpoints use it

| Endpoint | `Idempotency-Key` |
|---|---|
| `POST /invoices` | **Required** |
| `POST /invoices/{id}/finalize` | **Required** |
| `POST /invoices/{id}/send` | **Required** |
| `POST /invoices/{id}/pay` | **Required** |
| `POST /invoices/{id}/void` | **Required** |
| `POST /invoice-items` | **Required** |
| `POST /customers` | Optional. Honoured if you send it. |
| `POST /products` | Optional |
| `POST /prices` | Optional |
| `POST /webhook-endpoints` | Optional |
| All `GET`, `PATCH` and `DELETE` requests | Not used. Ignored if sent. |

Required endpoints are the ones that spend an invoice number, send an email, record a payment, or create something you'd have trouble telling apart from a duplicate. A retried draft create would give you two identical drafts, and no way to know which one to finalize. `PATCH` and `DELETE` are naturally idempotent: running them twice ends in the same state.

## What happens on each request

| Situation | Response |
|---|---|
| Required endpoint, no key sent | `428` with `code: "idempotency_key_required"`. Nothing runs. |
| First time we see this key | The request runs normally. If it succeeds (status below `400`), we store the response. |
| Same key, same body, first request finished | The stored status and body are **replayed**, with the header `Idempotent-Replayed: true`. Nothing runs again. |
| Same key, first request still in progress | `409` with `code: "conflict"`: *"A request with this Idempotency-Key is still in flight. Retry in a moment."* |
| Same key, **different** request | `422` with `code: "validation"` and an `errors` entry for the path `Idempotency-Key`. |
| Same key, first request failed | Failed responses (status `400` or higher) aren't stored, and the key is released, so a retry with the same key runs again. |

A "different request" means a different HTTP method, path or raw body. We hash all three, so reusing a key on a different endpoint, or with a body that differs by a single byte, is a mismatch.

```json 422 key reused with a different body
{
  "type": "https://invoice.horizonpay.co/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "This Idempotency-Key was already used with a different request body.",
  "instance": "req_…",
  "code": "validation",
  "errors": [
    {
      "path": "Idempotency-Key",
      "message": "Generate a new key per distinct request, not per retry loop."
    }
  ]
}
```

## Key rules

- **Up to 255 characters.** We recommend a UUID v4. A longer value is treated as if you sent no key, so a required endpoint returns `428`.
- **Scoped to your account**, not to one API key. Two different keys of yours that send the same `Idempotency-Key` share it.
- **Kept for 24 hours.** After that, the same key starts fresh.
- **The replayed body is the stored JSON.** It's the response as it was the first time, not the resource's current state. Fetch the resource if you need its latest state.

## Retry guidance

<Steps>
  <Step title="Generate the key once per logical operation">
    Create the key *before* your retry loop, not inside it. One invoice to finalize means one key, however many attempts it takes.
  </Step>
  <Step title="Retry with the same key and the same body">
    Retry on network errors, timeouts, `409 conflict`, `429`, `500` and `502`. Back off between attempts, and for `429` wait at least `Retry-After` seconds.
  </Step>
  <Step title="Check Idempotent-Replayed">
    If a response has `Idempotent-Replayed: true`, the original request already did the work. For finalize, the invoice number in the body is the one assigned the first time.
  </Step>
  <Step title="Use a new key for a new operation">
    Finalizing a second invoice, or sending a changed body, needs a new key.
  </Step>
</Steps>

<CodeGroup>
```javascript JavaScript
async function finalizeInvoice(id) {
  const key = crypto.randomUUID(); // once, outside the loop

  for (let attempt = 1; attempt <= 5; attempt++) {
    try {
      const res = await fetch(`${BASE}/invoices/${id}/finalize`, {
        method: "POST",
        headers: { ...headers, "Idempotency-Key": key },
      });
      if (res.ok) return (await res.json()).data;

      if (![409, 429, 500, 502].includes(res.status)) {
        throw new Error((await res.json()).detail); // not retryable
      }
      const wait = Number(res.headers.get("retry-after") ?? 2 ** attempt);
      await new Promise((r) => setTimeout(r, wait * 1000));
    } catch (err) {
      if (attempt === 5) throw err; // network error on the last try
    }
  }
}
```

```python Python
import time, uuid

def finalize_invoice(invoice_id):
    key = str(uuid.uuid4())  # once, outside the loop

    for attempt in range(1, 6):
        try:
            res = session.post(
                f"{BASE}/invoices/{invoice_id}/finalize",
                headers={"Idempotency-Key": key},
                timeout=30,
            )
        except requests.RequestException:
            if attempt == 5:
                raise
            time.sleep(2 ** attempt)
            continue

        if res.ok:
            return res.json()["data"]
        if res.status_code not in (409, 429, 500, 502):
            raise RuntimeError(res.json()["detail"])  # not retryable
        time.sleep(int(res.headers.get("Retry-After", 2 ** attempt)))

    raise RuntimeError("gave up after 5 attempts")
```
</CodeGroup>

<Note>
  Finalizing has a second safeguard. If an invoice already has a number, finalizing it again returns that same number instead of assigning a new one. So even a retry without a key can't spend a second number on the same invoice.
</Note>
