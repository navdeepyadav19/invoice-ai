The API uses conventional HTTP status codes: `2xx` for success, `4xx` for problems with the request, and `5xx` for problems on our side or with a provider we depend on.

Every error body uses the [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) `application/problem+json` format. It's the same shape on every endpoint:

```json
{
  "type": "https://invoice.horizonpay.co/problems/invalid-state",
  "title": "Invalid state for this operation",
  "status": 409,
  "detail": "This invoice has been finalized and can no longer be edited.",
  "instance": "req_4f0c2a9e8b7d4c1fa3e2b6d9c0e1f2a3",
  "code": "invalid_state"
}
```

<ResponseField name="type" type="string">
  A URL that identifies the problem type. It's `https://invoice.horizonpay.co/problems/` followed by `code` with underscores turned into hyphens.
</ResponseField>
<ResponseField name="title" type="string">
  A short summary of the problem type. It's the same for every error with a given `code`.
</ResponseField>
<ResponseField name="status" type="integer">
  The HTTP status code, repeated in the body.
</ResponseField>
<ResponseField name="detail" type="string">
  A human-readable explanation of this particular error. The wording can change, so don't parse it.
</ResponseField>
<ResponseField name="instance" type="string">
  The request id. It matches the `X-Request-Id` response header. Quote it if you contact support.
</ResponseField>
<ResponseField name="code" type="string">
  The stable, machine-readable error code. **Branch on this field**, not on `detail` or `title`.
</ResponseField>
<ResponseField name="errors" type="array">
  Only present when there are field-level problems, usually on `422`. Each entry is `{ "path": string, "message": string }`, where `path` is a dot-separated field path such as `items.0.unit_amount`.
</ResponseField>

## Error codes

| `code` | HTTP status | `title` | When it happens |
|---|---|---|---|
| `validation` | `422` | Validation failed | The body failed validation, isn't valid JSON, or a business rule rejected an input value. See `errors` for the fields. Also returned when an `Idempotency-Key` is reused with a different request. |
| `unauthorized` | `401` | Unauthorized | The API key is missing, malformed, unknown, revoked or expired. Includes `WWW-Authenticate: Bearer realm="invoice-ai"`. See [Authentication](/authentication#authentication-errors). |
| `forbidden` | `403` | Insufficient scope | The key is valid but doesn't have the scope this endpoint needs. Includes `WWW-Authenticate: Bearer`. |
| `not_found` | `404` | Not found | No such resource, **or it belongs to another account**. We never return `403` for someone else's id, so ids can't be discovered by probing. |
| `invalid_state` | `409` | Invalid state for this operation | The resource exists but is in the wrong state, for example editing a finalized invoice or voiding a paid one. See [Invoice lifecycle](/invoice-lifecycle). |
| `conflict` | `409` | Conflict | A uniqueness or concurrency clash, for example a request with the same `Idempotency-Key` that's still in progress. |
| `idempotency_key_required` | `428` | Idempotency-Key required | This endpoint requires an `Idempotency-Key` header and the request didn't send one. See [Idempotency](/idempotency). |
| `rate_limited` | `429` | Too many requests | You've gone over a rate limit. Includes `Retry-After`. See [Rate limits](/rate-limits). |
| `internal_error` | `500` | Internal server error | Something unexpected went wrong on our side. The detail is always generic. Quote the `instance` id. |
| `upstream_failed` | `502` | Upstream service failed | A service we depend on failed, such as the email provider or the database. For example, a finalized invoice whose email couldn't be sent. |

<Note>
  `409` has two codes. `invalid_state` means the operation can never succeed in the resource's current state. `conflict` means the request clashed with another one, and retrying later may work.
</Note>

## Validation errors

A `422` names each field that failed:

```json
{
  "type": "https://invoice.horizonpay.co/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "Some fields need attention.",
  "instance": "req_9a1b2c3d4e5f60718293a4b5c6d7e8f9",
  "code": "validation",
  "errors": [
    { "path": "customer", "message": "Invalid input: expected string, received undefined" },
    { "path": "items.0.unit_amount", "message": "Use whole minor units" }
  ]
}
```

## Handling errors

<CodeGroup>
```javascript JavaScript
const res = await fetch(url, init);

if (!res.ok) {
  const problem = await res.json(); // application/problem+json

  switch (problem.code) {
    case "validation":
      // Show problem.errors[].path / .message next to your form fields
      break;
    case "rate_limited":
      await sleep(Number(res.headers.get("retry-after")) * 1000);
      break; // then retry
    case "upstream_failed":
    case "internal_error":
      // Transient. Retry with backoff, reusing the same Idempotency-Key
      break;
    default:
      throw new Error(`${problem.code}: ${problem.detail} (${problem.instance})`);
  }
}
```

```python Python
res = session.post(url, json=body, headers=headers)

if not res.ok:
    problem = res.json()  # application/problem+json
    code = problem["code"]

    if code == "validation":
        for err in problem.get("errors", []):
            print(err["path"], err["message"])
    elif code == "rate_limited":
        time.sleep(int(res.headers["Retry-After"]))  # then retry
    elif code in ("upstream_failed", "internal_error"):
        pass  # transient: retry with backoff, reusing the same Idempotency-Key
    else:
        raise RuntimeError(f"{code}: {problem['detail']} ({problem['instance']})")
```
</CodeGroup>

## Which errors are worth retrying

| Retry? | Codes |
|---|---|
| Yes, with backoff | `rate_limited` (wait for `Retry-After`), `conflict` from an in-flight idempotent request, `upstream_failed`, `internal_error` |
| No. Fix the request first | `validation`, `unauthorized`, `forbidden`, `not_found`, `invalid_state`, `idempotency_key_required` |

When you retry a write, **send the same `Idempotency-Key`** so the retry can't do the work twice. A failed request (any status of `400` or higher) doesn't store a response, so a retry with the same key runs again.

## Request ids

Every response from an authenticated endpoint, success or error, carries an `X-Request-Id` header. You can send your own `X-Request-Id` (up to 200 characters) and we'll use and echo it. That makes it easy to connect your logs with ours. Otherwise we generate one of the form `req_<32 hex characters>`.
