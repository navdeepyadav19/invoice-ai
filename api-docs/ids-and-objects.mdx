## The response envelope

A successful response puts its payload under `data`. It's a single object for one resource, or an array for a list. Paginated lists add [`next_cursor`](/pagination).

```json
{ "data": { "id": "cus_9f8e7d6c5b4a39281706f5e4", "object": "customer", "name": "Globex Corporation" } }
```

`DELETE /invoices/{id}` and `DELETE /webhook-endpoints/{id}` return `204 No Content` with no body. The other `DELETE` endpoints archive the resource and return it.

## Id prefixes

Most resources have a prefixed public id. Their paths and reference fields also accept the resource's internal UUID, so you can use either form.

| Resource | Public id | Shape | Also accepts UUID |
|---|---|---|---|
| Customer | `cus_…` | `cus_` + 24 letters and digits | Yes |
| Invoice | `in_…` | `in_` + 24 letters and digits | Yes |
| Invoice item | `ii_…` | `ii_` + 24 letters and digits | Yes |
| Product | `prod_…` | `prod_` + 16 to 32 letters and digits | Yes |
| Price | `price_…` | `price_` + 16 to 32 letters and digits | Yes |
| Webhook endpoint | UUID | `8f14e45f-ceea-467a-9575-…` | UUID only |
| Business | UUID | | Read-only, no lookup by id |
| Invoice event | UUID | | Returned by `GET /invoices/{id}/events` |

Accepting UUIDs matters mainly for [webhooks](/webhooks#payload), because their payloads carry the invoice's and customer's **UUIDs**, not the prefixed ids. `GET /invoices/{uuid}` works with them directly.

<Tip>
  Store ids exactly as the API returns them, and treat them as opaque strings. A value that matches neither a prefixed id nor a UUID isn't a valid id.
</Tip>

## The `object` field

Customers, products, prices, invoices and invoice items include an `object` field naming their type: `customer`, `product`, `price`, `invoice` or `invoiceitem`. Business profiles, webhook endpoints and events don't have one.

## Money

Every amount in a request or response is an **integer in minor units**. There are no decimals and no floats.

| You mean | Send |
|---|---|
| $1,500.00 | `150000` |
| ₹29,500.00 | `2950000` |
| €0.99 | `99` |

- The API always uses **two implied decimal places**, whatever the currency. Amounts are stored with two decimals, and the wire value is that amount × 100.
- `unit_amount` must be a whole number of at least `0`. A fraction like `1500.5` is rejected with `422` (`"Use whole minor units"`).
- Invoice totals (`subtotal`, `discount`, `taxable`, `tax`, `total`, `amount_due`) and line `amount` and `tax_amount` values are worked out by the server and come back in minor units too.
- `amount_due` equals `total` while an invoice is `open` or `overdue`, and it's `0` for `draft`, `paid` and `void` invoices.

<Warning>
  One exception: the `data.total` field in [webhook payloads](/webhooks#payload) is in **major units** (for example `29500` or `29500.5`), not minor units. Convert it, or fetch the invoice for minor-unit totals.
</Warning>

### Percentages

`tax_rate` and `discount_percent` are plain percentages from `0` to `100`, such as `18` or `7.5`. They're not fractions and not basis points.

## Currencies

- Currencies are three-letter ISO 4217 codes. Input is trimmed and uppercased, so `usd` is accepted and stored as `USD`.
- An invoice created without `currency` uses your business profile's default currency.
- A priced line (`"price": "price_…"`) must be in the same currency as its invoice.

## Dates and times

- Calendar dates (`issue_date`, `due_date`, and the `from` and `to` filters) are `YYYY-MM-DD` strings.
- Timestamps (`created`, `updated`, `finalized_at`, `paid_at`, `voided_at`, `created_at`) are ISO 8601 strings in UTC.
- A new invoice's `issue_date` is the day it's created, in UTC. Set `due_date` directly, or pass `days_until_due` (0 to 365) on create to count forward from the issue date.

## Units

Line items take a `unit` of measure, which defaults to `NOS`. Allowed values are `NOS`, `PCS`, `KGS`, `GMS`, `LTR`, `MTR`, `SQF`, `SQM`, `HRS`, `DAY`, `MON`, `BOX`, `SET` and `OTH`.

## Archiving instead of deleting

Customers, products and prices are never hard-deleted, because issued invoices refer to them:

| Call | Effect |
|---|---|
| `DELETE /customers/{id}` | Archives the customer. It comes back with `"deleted": true` and is hidden from `GET /customers` unless you pass `include_deleted=true`. |
| `DELETE /products/{id}` | Archives the product. It comes back with `"active": false`. |
| `DELETE /prices/{id}` | Archives the price. It comes back with `"active": false`. |

Draft invoices, by contrast, really are deleted by `DELETE /invoices/{id}`. See [Invoice lifecycle](/invoice-lifecycle).
